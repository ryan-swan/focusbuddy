## A — §2.1 Migration · **VALID-WITH-CONDITIONS**

**What holds, with evidence:**
- Both verified starting states are real and exactly as characterized: factory-narrow `CHECK (kind IN ('folder', 'task'))` at `src/main/db/database.ts:33`; the legacy-widened quoted-`"nodes"` state matches GAP-REGISTER GAP-014 (lines 108–123), and I empirically confirmed a rename-based rebuild produces exactly that quoted-header fingerprint.

On legacy-widened DDL it fires; post-migration it skips (idempotent), including against the quoted-`"nodes"` DDL the V2 rebuild itself leaves behind.
- **The 4-kind target is load-bearing, not cosmetic**: empirically, copying the existing `task-item` rows (GAP-014's residue; 5 live per §2.1's F-m1, consistent with `analysis/cleanup-stuck-rows.log` + 9 trashed in `stuck-rows-backup.json`) into a 3-kind target throws mid-transaction — a boot-loop brick. The doc gets this exactly right.
- **Trigger-survival pin (F-M1) is a real, verified hazard**: `nodes_mark_dirty` (database.ts:741–744) dies with the table on rebuild; it is the sole dirty-marking mechanism for every main-process write (`markPushed` comment, workspaceSync.ts:465–466). The two-sided registration order (after `db.exec(SCHEMA)` :555, before trigger creation :740, before any work_item `ensureColumn`) is coherent at any position in that window because every `ensureColumn`/index-ensure re-runs each boot.
- **Rebuild pattern is proven in-house**: `migrateDocumentsDocTypeCheck` (database.ts:1215–1240) and `migrateShareKindChecks` (:1247–1300) already ship the exact `PRAGMA foreign_keys=off; BEGIN; create-new → copy → DROP old → RENAME new; COMMIT; foreign_keys=on` dance. I empirically confirmed both rename directions are FK-safe **only** because the pragma precedes the transaction — and that `PRAGMA foreign_keys=OFF` **inside** a transaction is a silent no-op, under which the rename direction becomes catastrophic (widgets' FK gets rewritten to `nodes_old`).
- **Receiver defensiveness matches the code**: all three apply sites (`applyRemote` :523, `applyRemoteOrg` :675, `applyRemoteShared` :764 in src/main/db/workspaceSync.ts) share the silent-swallow catch (:576–579, :734–737, :849–851) and the PRAGMA-intersection column drop (:559–560, :705–706, :809–810) — the "unknown-kind = infinite silent retry, unknown-column = silent blanking" characterization is exactly what the code does today. Both branches are trivially insertable at those sites. Per-row try/catch means an un-migrated peer's failure does **not** stall the cursor — the §8 residual-risk framing is honest about severity.
- Fresh installs: SCHEMA widened in-stage → born wide → predicate no-ops. Correct.

**Conditions (must be written into S1, else executed from memory):**
1. **`MIGRATION_VERSION` bump is nowhere stated** — database.ts:12 gates the pre-migrate `VACUUM INTO` backup on `user_version < MIGRATION_VERSION`; existing DBs are stamped 1, so without a bump to 2, §8's "backup-before-migrate" mitigation silently never fires for exactly the DBs the migration rebuilds. Zero mentions of MIGRATION_VERSION/user_version anywhere in planning/.
2. **Predicate no-match semantics unspecified** — a nodes DDL with no extractable `CHECK (kind IN (…))` clause (unanticipated shape): "absent" is vacuously true → fires → rebuild re-adds a CHECK that unknown kinds could violate → aborted txn every boot. Pin the safe default (skip + loud surface) explicitly.
3. **Add a post-migration FK-integrity assertion to the fixtures** (`PRAGMA foreign_key_check` clean + a widgets insert succeeds): the pragma-inside-txn no-op is the one breakage mode that data/index/trigger assertions all pass through, surfacing only at the later live smoke.
